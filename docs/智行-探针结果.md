# 智行火车票 · Phase 0 探针结果

分析对象：`com.yipiao` **10.25.8**（versionCode 710258，targetSdk 30，arm64-v8a，单 base.apk）。

> 本文是 Phase 0（只装探针、不改行为）的实测结果。探针代码见
> `app/src/main/kotlin/io/github/wuqiao309/clearapp/hooks/YipiaoHooks.kt`。
> 验证方式：`./scripts/dev.sh deploy yp`，或 `adb logcat -d | grep ClearApp/com.yipiao`。

## 一、架构判断（决定每条需求能不能做）

| 层 | 技术 | 覆盖的界面 |
| --- | --- | --- |
| 原生 | Android View | 底部 tab 栏（`ZTTabBarView`） |
| Compose | Jetpack Compose | 首页子 tab、首页部分模块、「我的」页 |
| CRN | 携程 React Native（Hermes） | 首页内容、抢票、订单、支付 |

关键结论：**原生/Compose 的部分可以直接 hook；CRN 页面（`rn_*.ctz`）的组件是 JS 渲染的，
Xposed 改不了视图树**，只能从数据层（网络响应 / CRN bridge）下手。

## 二、已挂探针（23 条，全部命中）

底栏、首页子 tab、首页模块、我的服务、订单弹窗、营销弹窗、支付弹窗、路由、订单浮球、原生广告。

### 底栏

`ZTTabBarView.setData(List<ZTTabEntity>)` 实测输出：

```
底栏 tab：首页 | 抢票 | 订单 | 我的
```

正好是需求要保留的四个，**底栏 tab 本身不用改**。

但真机截图里底栏中间还多一个活动位「超级星期二」（`ActivityTabView`）。它不在
`ZTTabEntity` 列表里，由 `HomePageActivityTabData.isInValidTimePeriod()` 控制：
返回 `false` 时 `addLocalActivityTabView()` 直接 return，活动位不创建。

### 首页子 tab

`AzureSetupManager.k()` 实测输出：

```
首页子 tab：home_train=火车票 | home_flight=机票 | home_stay=民宿/客栈 | home_hotel=酒店
```

`home_stay` / `home_hotel` 就是要删的两个。列表在 `initializeModules()` 里被克隆后重算
默认下标，所以在 `k()` 入口过滤是安全的。

### 首页内容模块

首页路由是 `/rn_ztrip_home/_crn_config?...`，内容由 CRN 渲染。
`ModuleManager.dispatchRequest`（原生模块分发）**没有触发** —— 说明「低价不怕比」及以下
不是原生模块，是 RN 组件。

### 抢票

CRN 页（`rn_robTicket`），顶部「候补管家 / 余票监控」是 RN 组件，原生层无对应入口。

### 订单

CRN 页（`rn_order`），信息流里的「加智行微信好友」「低价酒店」等卡片是 RN 组件。
原生侧只探到：

- `WaitPayFloatViewModel.fetchWaitPayOrders()` —— 订单待支付浮球，频繁调用
- `OrderGlossary.B(TravelOrderPopConfig)` —— 调用时 config 为 `null`（本版没下发该弹窗）

### 我的（Compose）

| 需求 | 组件 |
| --- | --- |
| 我的足迹 | `com.app.train.main.personal.compose.module.FootprintComposeKt` |
| 周边服务 | `com.app.train.main.personal.compose.module.MyNearbyComposeKt` |
| 右下悬浮球 | `com.app.train.main.personal.compose.header.HomeFloatComposeKt` |
| 我的工具（保留） | `MyToolComposeKt` |

注意：这些 composable 的方法名被混淆了（实测 `FootprintComposeKt.e(...)`、
`MyNearbyComposeKt.d(...)`、`HomeFloatComposeKt.f(...)`），**优先 hook 数据源**
（`MyCenterComposeViewModel` 的模块列表 / `fetchBuoyConfig`），别按混淆方法名写死。

### 弹窗

`HomeMarketingManager.processPopList` 启动时下发 4 条：

```
user-with-coupons（webview）
机票超级星期二（image）
周末游（json）
20230905-attracting-01（迷你程序）
```

`addDisplay` 对「20230905-attracting-01」触发了。营销弹窗/悬浮层统一从这里走。

`SaleInfoPayManager` 的 `h/i/k/m` 四个入口已挂，等待「去支付 → 基础抢票」流程验证。

`ZTRouter.openURI` 已挂，可捕获「已预约」前的邀请好友页 URL。

### 原生广告

`TripAdManager` 是统一的原生广告入口：

- `isShowTripAd()` —— 总开关
- `canShowAD(boolean)` —— 单个开关
- `checkAd(...)` / `showTimelySplashAd(...)` —— 启动时实测被调用
- `loadBannerAd(...)` —— 三个重载

**结论：原生广告有统一开关；CRN 信息流广告不在这个开关里**，需要单独做。

## 四、建议的实施顺序

1. **Phase 1（原生/Compose，稳）**
   - 首页子 tab 过滤
   - 超级星期二活动位
   - 我的页：足迹、周边服务、右下浮球
   - 原生广告总开关
2. **Phase 1.5（流程弹窗）**
   - 抓「已预约」「去支付」两条链路的路由和弹窗日志，确认后写规则
3. **Phase 2（CRN，单独专项）**
   - 先抓 `rn_ztrip_home` / `rn_robTicket` / `rn_order` 的接口响应
   - 评估「改响应 JSON」和「CRN bridge 注入」两条路，选一条
   - 这是工作量最大、也最容易被版本升级打断的部分

## 五、调试备注

- 智行的 CRN 页面会让 `uiautomator dump` 报 `could not get idle state`，读到的可能是旧 XML；
  以 `adb shell screencap` 截图为准。
- 模块只在 `com.yipiao` 主进程生效；`:pushservice`、`:hbccompilev2` 会打印日志后跳过。
- 作用域需要在 Vector 管理器里手动勾选 `com.yipiao`（`scope.list` 只是推荐范围）。

### 仍未解决

- **抢票页顶部「候补管家 / 余票监控」**：**用户决定暂时放弃**。CRN 渲染，View 层隐藏会被 RN
  重新渲染/预加载副本覆盖，需要 CRN 数据层（接口响应或 bridge）才能稳定处理。
- **CRN 信息流里的其他服务端推广**：首页/订单已处理文案可识别的部分；其余需要数据层。
- **统一广告开关**：原生 `TripAdManager` 已接入（`isShowTripAd` → false、banner 跳过）；
  CRN 信息流广告不走它，仍受服务端下发控制。
