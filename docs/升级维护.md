# 升级维护

app 升级后模块部分规则会失效，这份是「怎么发现、怎么定位、怎么修、怎么发版」的完整流程。

## 为什么一定会失效

番茄/红果的类名分两类：

- **可读的**：`com.dragon.read.*` —— 页面、服务、模型、枚举，名字是有意义的，**跨版本稳定**。
- **混淆的**：`r32.o`、`ma5.o` 这种 —— 底层组件，包号是打包时按顺序生成的，**每次升级都变**。

v1.0.0 发布于 7.3.7.x，之后两个 app 静默升到 7.3.9.32，结果：

```
r32.o  -> y32.o      红果一键领挂件的控制器
ma5.o  -> dd5.o      番茄发帖球
t76.i  -> hb6.i      书架子 tab 注册表
lc4.c  -> sd4.c      我的页卡片分发器
vv3.d  -> sw3.d      卡片信息类型
ig7.j / ve7.j  ->  直接消失（只是探针用，不影响功能）
```

**靠可读名的规则一条都没断。** 所以做规则时的第一原则是：**能用可读的锚点就别用混淆名**。

## 零、有些规则能自己救回来（DexKit 结构兜底）

规则挂载走的是 [ClassResolver.findMethodOrByShape]：**先按名字找，找不到再按结构找**。

- 按名字找是零开销的，平时都走这条。
- 结构查找（DexKit 扫 dex）**只在名字失效时才触发**。实测开销：bridge 创建 329 ms + 查询 54 ms。
- 结构特征用**框架类型**表达 —— `(android.view.ViewGroup, int, android.content.Context) -> void`。
  框架类型跨版本不变，所以混淆名改了也能找回来。

**实测**：把 `float-pendant-legacy-attach` 的目标故意写成旧版的 `r32.o`（7.3.9 里已经改叫 `y32.o`），
模块自己打印：

```
按结构找回 (android.view.ViewGroup, int, android.content.Context) -> void -> y32.o#t
已挂载 float-pendant-legacy-attach -> y32.o#t
```

而且它在番茄上也找出了 `n72.o#t` —— 番茄**其实也有**这套老式挂件（之前按名字的规则一直漏了它）。

**用结构兜底的前提是特征够独特**。同签名的方法往往不止一个，所以要：

- 排除框架自己的（`android.` / `androidx.` / `java.` / `kotlin.` 开头的包）
- 排除接口上的声明（不是实现）
- 用 `excluding` 列出「这条特征还会命中、但别的规则已经管了」的类
- **滤完还不唯一就放弃** —— 挂错一个比漏掉更糟

新写规则时，只要目标方法的形参表是框架类型，就顺手传一组结构特征；名字失效时它会自己兜住。

## 一、发现失效

模块对目标方法找不到是**容错**的：跳过该条、打一条日志，不影响别的规则、不崩溃。所以升级后
表现为「某几个东西又冒出来了」，而不是模块整个坏掉。

```bash
adb logcat -d | grep "ClearApp/"
```

看这两类行：

```
跳过 <规则>：目标方法不存在          ← 这条断了，要修
已挂载 <规则> -> <类>#<方法>        ← 这条好的
```

`跳过` 的条数就是这次要修的数量。

## 二、定位新名字

按「可读锚点 → 顺藤摸瓜」的顺序找，别靠类长得像不像。

### 手法 1：从可读的服务/入口往下找

红果一键领就是这么修的：可读的 `PendantFloatTipsServiceImpl` 没变，但底下控制器改名了。

先在反编译结果里找**可读的那个类**，看它 new 出什么、调了什么：

```
PendantFloatTipsServiceImpl
  → new h0(context, cVar)          (c42.h0，这是另一个挂件，不是要找的)
```
```
CommunityInfiniteEditorHelper#b()
  → new dd5.o(this.a)              ← 这才是发帖球
```

**关键经验**：7.3.9 改版时先按旧版特征找出了 `o24.o` 看着很像，实际是 `dd5.o`。**认对象要看
「谁被建它的那个方法 new 出来」**，不要看长得像。

### 手法 2：按形参个数找方法

参数多到十几个的入口（挂件的 `tryShowFloatTips` 有 15 个），逐个列类型又啰嗦又容易错。
用 `ClassResolver.findMethodByArity(类名, 方法名, 形参个数)` —— **方法名来自可读接口、参数个数
也稳定**，按这两样找就够了。

### 手法 3：从 app 内部把视图树打出来

`uiautomator` 和 `dumpsys activity top` 在视频类 app 上经常不灵（前者拿不到 idle、后者超时），
而且它们对自定义 View 只报基类名（`android.widget.RelativeLayout`）。

最可靠的是**在模块里挂 `Activity#onResume`，延迟几秒后从 `decorView` 遍历**，按屏幕位置把节点
打出来：

```kotlin
hooks.intercept("probe-viewtree", onResume) { chain ->
    val result = chain.proceed()
    (chain.thisObject as? Activity)?.let { activity ->
        Handler(Looper.getMainLooper()).postDelayed({
            // 遍历 activity.window.decorView，按 getLocationOnScreen 的坐标过滤
        }, 10_000)
    }
    result
}
```

红果的一键领球就是这么定到的：屏幕右侧中部 138×264 的那个节点，类名是 `c42.e`。

### 手法 4：挂构造函数打调用栈

`HookManager.interceptConstructors(id, 类, body)` —— 用来回答「这个视图到底是谁建的」。
在回调里打一条 `Throwable().stackTrace`，上层调用者一目了然，比翻反编译快，也不受混淆影响。

### 手法 5：用日志 tag 反查

两个 app 里留了大量可读的日志 tag（`CardDispatchManager`、`provideCard`、`GlobalPlayerView`、
`FloatBallLayoutDebug`…）。在 dex 里 grep 这些字符串，能直接定位到类 —— 混淆的是类名，不是日志。

## 三、常见锚点对照

| 要找什么 | 可读的锚点 | 说明 |
| --- | --- | --- |
| 底部 tab | `com.dragon.read.pages.main.m#c(...)` | 全可读，从没断过 |
| 书城子 tab | `com.dragon.read.model.BookMallDefaultTabData#a(...)` | 全可读 |
| 我的页入口 | `IBsMineTabCellService#isCellTypeShowable(int)` | 接口可读，挂运行时实现类 |
| 挂件（两套） | `PendantController` / `PendantFloatTipsServiceImpl` | 服务可读，控制器混淆 |
| 发帖球 | `CommunityInfiniteEditorHelper` | 建球的 `b()` 可读 |
| 卡片分发器 | 日志 tag `CardDispatchManager` | 类名全混淆，靠 tag 反查 |

## 四、修完怎么发版

```bash
# 1. 改版本号（两处都要改）
#    app/build.gradle.kts  : versionCode / versionName
#    META-INF/xposed/module.prop : version / versionCode

# 2. 构建 + 装机验证
export JAVA_HOME="C:\Program Files\Java\jdk-21"
./gradlew.bat clean assembleRelease
adb install -r app/build/outputs/apk/release/app-release.apk

# 3. 看日志确认没有「跳过」了
adb logcat -d | grep "ClearApp/"

# 4. 提交推送
git add -A && git commit -m "fix: 适配 <app> <版本>"
git tag v<版本> && git push && git push origin v<版本>

# 5. 两个 release
gh release create v1.0.2 dist/ClearApp-v1.0.2.apk \
  --title "ClearApp v1.0.2" --notes-file docs/发布说明-v1.0.2.md

# LSPosed 仓库的 tag 格式是 versionCode-versionName
gh release create 3-1.0.2 dist/ClearApp-v1.0.2.apk \
  --repo Xposed-Modules-Repo/io.github.wuqiao309.clearapp \
  --title "1.0.2" --notes-file docs/发布说明-v1.0.2.md
```

发布说明照 `docs/发布说明-v1.0.1.md` 的样子写，开头列清楚「这一版为什么发」。

## 五、踩过的坑

**模块装完第一次冷启可能仍跑旧版本。** Vector 需要一点时间重新读模块，这时候冷启目标 app，
日志里可能一条规则都没有。再 force-stop 重启一次即可 —— 别以为是规则写错了。这个坑在调试时
浪费过一整轮。

**改完代码别忘了 force-stop 目标 app。** 模块在进程启动时装 hook，app 不重启就还是旧的。

**`uiautomator dump` 在播放中的视频上会报 `could not get idle state`**，先点一下暂停再抓。
`dumpsys activity top` 在设备负载高时会 `DUMP TIMEOUT`。

**`autoHotReload` 在这套环境里不生效（查到底了，但没解决）。** 指望它省掉每次改完代码的
force-stop + 重启，把两次失败的结论和排查过程记下来，省得下次重走：

已经确认的事：

1. **Vector 2.2 是有热重载实现的** —— daemon 里能搜到 `autoHotReload` 的解析代码、
   `IHotReloadCallback` / `IHotReloadOutcomeReceiver` 两个 IPC 接口，还有
   「has no hot reload entry point」「A reload is already running」这类文案。所以不是「框架没做」。
2. **重装模块 APK 后 daemon 毫无反应** —— 清空框架日志（`cli log clear`）再重装模块，日志是**空的**，
   连一次模块扫描都没有。
3. **没有 CLI 命令能触发** —— `vector-cli` 只有 status / modules / scope / config / db / log。
4. **管理器 App 根本没装** —— `pm list packages` 里没有任何 vector/matrix 包，`manager.apk` 只是躺在
   `/data/adb/modules/zygisk_vector/` 里没被安装。而 `IHotReloadCallback` 是 **service 接口**，
   热重载很可能是由管理器发起的。
5. **daemon（`vectord`）是 `service.sh` 在开机时启动的，没有守护进程** —— 手动杀掉到重启前都不会恢复。

两个嫌疑，都需要**重启手机**才能区分：

- daemon 是在**开机扫描模块时**读的 `module.prop`。我们的模块最早装上时 `autoHotReload=false`，
  后来改成 `true` 再重装模块并不能让它重新扫 → 要重启 daemon 才生效。
- 热重载要靠**管理器**发起，而管理器没装。

**没有去重启验证**：这台机器是月虹提权助手的**临时 root**，重启要重新提权，成本不该由我替你决定。
开关已经关回 `false`。哪天想试，**先装管理器**（`adb install /data/adb/modules/zygisk_vector/manager.apk`）
再重启，然后用一个**真的换了二进制**的包测 —— 别被 Gradle 的 up-to-date 骗了。

**红果上那个老式挂件的服务入口是死的。** `PendantFloatTipsServiceImpl#tryShowFloatTips` 挂着
可读名、看着最该是入口，实测**一次都不触发** —— 球是控制器 `y32.o` 直接建的。所以「可读名的
入口」不一定就是真正生效的路径，**挂上不等于触发，一定要看命中日志**。为此 `replaceBoolean`
这类规则现在每次命中都记日志。
